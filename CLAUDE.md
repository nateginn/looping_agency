# Loop Agency — operating instructions

This workspace runs durable business loops (build → verify against a real KPI → learn → repeat) for onboarded client projects. Full design and rationale: `AgentColabPlan.md`. Review history: `PLAN-REVIEW-LOG.md`. Open findings and risk acceptances: `RISK-REGISTER.md`. Read all three before making structural changes here.

**Selected operating model for getting an approved change live: Path B — direct push to the deployment branch, then post-deploy health verification, rollback on failure, and notification through MMC's daily briefing.** Read `PLAN.md`'s "SELECTED OPERATING MODEL" section before touching anything on that path; most of the rest of `PLAN.md` describes Path A (side branch → PR → GitHub auto-merge) and is marked `[HISTORICAL — PATH A]`. `tools/publish.py` and the branch-protection/PR/auto-merge block of `tools/lib/github_compare.py` implement Path A and are **dormant by decision** — complete, tested, unreachable, and structurally unable to perform Path B (`publish.py` refuses a `main`/`master` destination by construction). Do not delete them; do not build on them. **Path B itself is not built: nothing in this workspace pushes anything, and R6's Tier-2 boundary has not been amended to permit it.** The autonomous half that *is* live is everything up to the local commit (`/codex-seo-review` → `apply.py`, see Phase 7 below).

## Environment setup

A project-local virtual environment lives at `.venv/` (gitignored — never commit it). Dependencies are pinned in `requirements.txt`: PyYAML, keyring, google-auth + requests (GSC service-account token minting), and truststore (Windows cert store for live HTTPS — see RISK-REGISTER.md R8).

```
python -m venv .venv                              # first time only
./.venv/Scripts/python.exe -m pip install -r requirements.txt   # first time / after requirements.txt changes
./.venv/Scripts/python.exe tools/run_loop.py <project> <loop>   # run any tool through the venv
```

Run tools through `.venv/Scripts/python.exe`, not a bare `python`, so the pinned dependency versions are what actually execute.

## The run contract (every run, every loop)

1. Acquire the per-loop run lock (`tools/lib/lock.py`). A live lock refuses the run and logs the refusal to `lock-refusals.log`. A stale lock (dead PID or age > `max_run_duration_minutes`) is auto-recovered: archived under `runs/<old-run-id>/stale-lock.json`, never manually deleted.
2. Validate `spec.md`'s YAML frontmatter against the schema (`tools/spec_validate.py`). An invalid spec refuses to run before anything else happens.
3. Load `memory.md` and the pending proposals (the experiment register).
4. Pull metrics via the loop's connector; write an immutable, redacted, timestamped snapshot under `runs/<run-id>/snapshot.json` (`tools/snapshot.py` — read-only file mode). **Connector failure is classified, not uniform** (`connector_registry.py`'s `critical` flag, added 2026-08-10): a *critical* connector (`gsc`, `dataforseo`, `mock` — the sources that feed `search_analytics`) still aborts the whole run as `partial-failure`, writing no snapshot, because evaluating proposals against a carried-forward stale section is the false-win failure mode Phase 1 exists to prevent. An *enrichment* connector (`pagespeed`, `gsc-indexation`, `dataforseo-local-rank`, `dataforseo-backlinks`) instead degrades the run: its failure is recorded as a failed `tool_call`, named in `degraded_connectors` and in report.md's Needs Attention, its snapshot section is carried forward from the previous run, run status becomes `degraded`, and the evaluation/proposal steps continue. `pagespeed.py` additionally retries transient 5xx/transport failures (3 attempts, 2s/5s backoff; never retries a 4xx).
5. Evaluate prior `applied` proposals whose observation window has elapsed and sample size is sufficient. A guardrail breach halts the loop (`state.json: paused-breach`) and blocks all new proposals until a human resolves it via `/review-pending --resolve-breach`.
6. Cooldown: no new proposal targets a page/asset that already has an `applied` proposal still inside its observation window.
7. Pick up to 3 new proposals from `allowed_actions` (skipped entirely if `paused-breach`); write them to `pending/` as `draft`.
8. Write `runs/<run-id>/run.json` (structured, redacted) + `report.md` (human-readable); append one summary line to `memory.md` (a derived view — `runs/` is the system of record). Release the lock.

**Approval state machine:** `draft → reviewed → approved → applied → verified` (or `rejected` / breach → revert proposal). Only `/review-pending` + explicit human approval can move a proposal to `approved`; only `tools/apply.py`, and only on an `approved` Tier ≤ 1 proposal, performs `applied`. Tier 2 proposals are never applied by tooling — human-only, always, including any `git push` to a repo that auto-deploys with no staging gate (see RISK-REGISTER.md R6). **Phase 7 (dormant by default, see above) adds a parallel path**: `draft → review-pending → [review-revision-needed →]? review-approved|review-rejected|review-held|approved-for-implementation`, converging on `apply.py` only from `approved-for-implementation` (never `approved` — the human and Codex-review paths write distinct proposal fields, `decision` vs `review`/`auto_implementation`, and are never conflated). A human can rescue any of these states into `approved`/`rejected` via the unchanged `/review-pending`.

## Tools (`tools/`)

- `spec_validate.py` — schema validator, `--verify` self-test.
- `lib/lock.py` — run lock + stale-lock recovery, `--verify` self-test.
- `lib/redact.py` — alias-based + pattern-based secret redaction, `--verify` self-test.
- `lib/paths.py` — canonical (symlink-resolved) path containment checks; every project/loop path is checked with `assert_within` before use.
- `snapshot.py` — immutable redacted metrics snapshot writer, `--verify` self-test.
- `lib/credentials.py` — credential resolver: Windows Credential Manager (keyring, service `loop-agency`) first, then `projects/<slug>/.env` gated behind an `icacls` ACL check that refuses any principal beyond current user + SYSTEM/Administrators. CLI: `--store <alias>` (interactive, how the human hands over secrets), `--check <alias> [--project <slug>]` (never prints values), `--verify` self-test.
- `lib/errors.py` — shared `ConnectorError` (re-exported from `mock_metrics.py` for compat).
- `mock_metrics.py` — synthetic connector for `_demo` only; supports `normal`/`breach`/`fail` scenarios. Never calls a real API.
- `gsc.py`, `dataforseo.py` — real connectors, dispatched per `spec.inputs` entry by `run_loop.py`'s `_fetch_metrics` since Phase 2 Step 2. GSC is the primary metrics source; DataForSEO only enriches matching (keyword, page) rows with `serp_position`. Both redact internally and refuse to run without a credential resolver.
- `smoke_test.py` — connectors-only smoke test (`python tools/smoke_test.py <project>`): resolves each alias (reports which store answered, never the value), calls each connector live once, prints a redacted summary, includes a bad-alias clean-failure simulation. Writes nothing under `runs/`; takes no lock. `--verify` self-test.
- `run_loop.py` — the run contract engine described above.
- `review_pending.py` — approve/reject/list proposals, resolve a breach.
- `apply.py` — for an approved, opted-in Tier-1 proposal, performs the local `implemented` transition: a read-only `git fetch origin` to confirm the local `main` matches `origin/main` (refuses on drift, Phase 5), then an isolated `git worktree` commit on an unpushed branch. Never pushes, merges, or deploys — those stay Tier 2, human-only (R6). Re-checks approval and tier itself regardless of caller.
- `publish.py` — Phase 6. For an `implemented` proposal with a recorded human approval (`decision.action` of `approve`/`retry`, already written by `review_pending.py`), re-verifies commit ancestry, diffs the commit's own git objects (not the working tree) to confirm exactly one changed file whose blob contains the approved `new_value`, confirms the local branch hasn't moved, checks `.github/workflows/deploy.yml`'s trigger shape at the base commit, validates `origin`'s push URL against the expected `owner/repo`, and hard-refuses unless GitHub's branch-protection API confirms `main` is fully locked down — then pushes the commit to a fully-qualified `seo/<id>` ref, opens a PR via `lib/github_compare.py`'s `create_pull_request()`, and requests auto-merge via `enable_auto_merge()` (GraphQL `enablePullRequestAutoMerge` — no `gh` CLI dependency). Never pushes/merges to `main`/`master` itself; branch protection plus GitHub's own required-review gate is the actual boundary (`PLAN.md` "Where the security boundary actually is"). Token via `credentials.py` alias `<project>-github-token`. Re-acquires the shared run lock like `apply.py`/`review_pending.py`. The PR/auto-merge path is not wired to any project.
- `deploy_health.py` / `deploy_verify.py` — Phase 6a offline-tested health and rollback orchestration. Records new and previous deployment SHAs, uses a non-blocking stabilization window, runs bounded public-site checks, persists redacted results, and models rollback/escalation through an injected redeploy hook. The default hook refuses; no project is wired to deploy or rollback automatically, and `art` remains propose-only/manual-approval-only.
- `watchdog.py` — out-of-band scheduling watchdog (Tier 0, local-only, read-only); checks that each active loop's expected run artifact exists for its cadence window. "Active" is now enforced: it reads `loops_enabled` from `projects/<slug>/project.md` and reports a loop absent from that list as `not-enabled` rather than alerting on it (2026-08-10 — `_demo` is an on-demand fixture and was firing a false alert every single day). This is the only code that reads `loops_enabled`; `run_loop.py` deliberately does not, so a disabled loop stays runnable by hand.
- `scheduled/task.cmd` — the wrapper every Windows Task Scheduler job runs through. Resolves the workspace root from its own path, pins `.venv\Scripts\python.exe`, appends stdout+stderr to `logs/<name>.log` (rotating at 2 MB), and exits with the child's code. Registration commands and the collision/redirection history are in `PHASE3-SCHEDULING.md`.
- `lib/action_types.py` — Phase 7: `IMPLEMENTABLE_ACTIONS`, extracted from `apply.py` into a neutral module both it and `lib/review_protocol.py` import, avoiding a circular import.
- `lib/event_log.py` — Phase 7: append-only, redacted, per-loop event log (`events.jsonl`). Source of truth (event-sourced) for the review subsystem's `status`/`review`/`implementation` projection (`sync_proposal_projection`, `rebuild_review_rounds_from_events`); best-effort observability layered onto the pre-existing state machine elsewhere (`--reconcile`). Tail-corruption is quarantined (`events.jsonl.quarantine`), never deleted; any malformed/schema-invalid line anywhere in the log sets a global `events.jsonl.corrupt_marker` that fails closed for authorization-adjacent reads. `--verify` self-test (26 checks).
- `lib/review_protocol.py` — Phase 7: deterministic, LLM-free evidence-packet building, hash computation (`proposal_content_hash`/`evidence_packet_hash`/`spec_content_hash`), pass-based adjudication (`adjudicate`, selecting by `pass_number` not content hash — a revision that returns to its exact original content must not collide two passes), and `evaluate_auto_implementation_eligibility()` (authorizes tier/`manual_approval_only` from the *current* spec's `allowed_actions` entry, never a proposal's own cached fields). Never calls Codex itself. `--verify` self-test (22 checks).
- `codex_review_proposal.py` — Phase 7: the only tool a Claude session shells out to for review-pipeline state mutation (`--start-review`/`--evidence-packet`/`--record-round`/`--adjudicate`/`--auto-implement`, all `<project> <loop> <id>`). Persists one evidence-packet artifact per pass (`pending/.review-artifacts/<id>-pass<N>.json`, refuses to overwrite). Never calls Codex — see `.claude/skills/codex-seo-review/SKILL.md` for the actual `codex exec` invocation.
- `draft_link.py` — Phase 7: `draft_copy.py`'s counterpart for `internal-link-addition` (`source_page`/`destination_page`/`anchor_text`, validated against `priority_pages`/`noindex_destination_pages`). Still never implements an HTML mutation. `--verify` self-test (17 checks).
- Scripts import each other via flat imports (e.g. `from lib.redact import redact_deep`) and are invoked as direct file paths (`python tools/run_loop.py ...`), not as an installed package — run them from the workspace root.

## Secrets & tenant isolation

Windows Credential Manager is the default secret store; per-project `.env` is an explicit fallback only, requires restricted ACLs, and the runner must refuse to start against an over-broad `.env`. Repo files store only opaque aliases, never raw values. A run may only read/write inside `projects/<slug>/` and its declared repo, checked via resolved canonical paths (`tools/lib/paths.py`) — never naive prefix matching.

## Debugging

Never rely on model memory to reconstruct what a run did — `runs/<run-id>/run.json` is the observability contract. If something looks wrong, read that file (and `snapshot.json`, `report.md`) before speculating.
